# DishNest publisher signing

O. Bankole explicitly authorized creation of the permanent release key on 19 October 2026. `tools/sign_publisher_release.ps1` initially created it in the Git-ignored `.local-signing` directory, then moved it with hash verification to `%LOCALAPPDATA%/DishNest/publisher-private/.local-signing` on NTFS. The project drive is exFAT and cannot enforce ACLs. The directory permits only the current Windows account and SYSTEM. The key password is generated from 48 random bytes and stored as a Windows DPAPI-encrypted PSCredential, never in Git, APKs, source archives or command-line arguments. The alias is `dishnest-release`.

The script refuses a partial setup and refuses a certificate change when prior evidence exists. Run it again to sign a newly verified unsigned build with the same key. It checks current build provenance, APK signature, certificate identity, 16 KB ZIP alignment and equality of every original ZIP payload. `tools/publisher_evidence.py` independently repeats the binary checks during packaging. Public fingerprint, validity and APK hashes are recorded in `artifacts/publisher-signing.json`.

## Required secure backup before release

Preserve `%LOCALAPPDATA%/DishNest/publisher-private/.local-signing/dishnest-release.jks` and the alias/password in a secure, encrypted backup under publisher control. Keep an independent recovery copy. Losing this identity can prevent future app updates.

The DPAPI `credentials.clixml` file can be decrypted only by the same Windows user on this computer. Copying that XML and the keystore alone is **not a portable recovery backup**. While this Windows account still works, the publisher can privately retrieve the credential using PowerShell's `Import-Clixml` and `GetNetworkCredential().Password`, then save it in a trusted password manager. Do not paste it into chat or a repository, or run that retrieval through an agent tool that records output. Verify the backup on a trusted recovery machine before submitting. Backup/recovery has not been certified.

## Recovery verification on the existing Fire

On 19 October the current user's persistent files were read twice without launching or stopping the ordinary app, compared for equality, archived in memory and encrypted with Windows DPAPI CurrentUser. The encrypted archive and a hash-verified copy of the original debug APK are under `%LOCALAPPDATA%/DishNest/publisher-private/fire-recovery` on NTFS, restricted to this Windows user and SYSTEM. This recovery copy is machine/account-bound, not a portable backup. No customer file contents, account identifiers or private file hashes are committed.

`python tools/check_fire_recovery.py` decrypts the latest archive in memory, requires an exact match to the ordinary app's current persistent files, and restores each file into a newly generated private cache directory of `com.dishnest.app.qa`. The original app is never launched, stopped, installed, cleared or uninstalled. Every transferred byte is read back and compared. A small Java probe then opens the copied database using the Fire's native SQLite implementation and requires `PRAGMA integrity_check` to pass. The original persistent files are compared again afterward. The device run passed for all five currently present files. Private diagnostic copies remain inside QA cache; they are not exported to shared storage. The generic archive limits and path checks do not make this an importer for arbitrary untrusted archives.

This proves private-file recovery into an isolated writable sandbox, **not restoration into the non-debuggable Amazon APK**. Android-managed keystore entries, permissions, alarms and notification settings are outside that archive. The current built-in kitchen importer also omits timers and app preferences. Do not remove the original installation on the strength of this diagnostic alone. Keeping the Amazon build with migrated data requires a separately verified import path; temporarily testing Amazon and returning to the original app requires a reviewed rollback procedure before removal.

The publisher subsequently explicitly chose **temporary Amazon testing followed by original-app/data restoration**. `tools/fire_temporary_lat.py prepare` bound the encrypted archive, original APK, one-device identity and captured permission/app-operation settings into an ACL-protected local plan. Only then was the original debug installation removed. The native Amazon Appstore delivered its separately signed release; `record-lat` verified its installer, non-debuggable package/version, signature and reviewed LAT verifier binding before recording the exact temporary APK. The Amazon certificate independently matched the console.

After targeted release and monthly purchase tests, `python tools/fire_temporary_lat.py restore` removed that exact recorded Amazon APK, installed the protected original APK, stopped it before raw-file restoration, copied every backed-up persistent file using the verified base64 transport, and read each file back. APK identity, the complete persistent-file map, captured runtime permissions and app-operation modes all matched. A second isolated recovery/native SQLite check on the restored data passed. The original app was left unlaunched so its final bytes remain exactly those captured before testing. `artifacts/fire-amazon-lat-qa.json` records completion without private contents or device/account identifiers. The encrypted backup and original APK remain protected locally. This completed temporary rollback is not a permanent migration into the Amazon build or a portable signing-key recovery test.

The publisher-signed billing-disabled release described above remains distinct from the billing-enabled private LAT candidate documented in `AMAZON_LAT.md`. Private LAT has been submitted; public release has not.
