# Translation review

The 21 October follow-up adds an authored duplicate-title format in all app locales, including separate resource sets for both English and Portuguese markets. Only the generated suffix is translated; the user's recipe title stays intact and remains editable. Meal-swap choices and pantry reminder labels now display valid ISO dates using locale month names/order/numerals; date entry and database values remain ISO, and unparseable legacy/user values are displayed verbatim. `authored/runtime-ui.tsv` retains the new format for offline resource assembly. Native-speaker and final UI approval remain pending.

The 20 October continuation replaces plain integer interpolation in recipe step numbers, serving controls and calendar days with active-resource-locale number formatting. Planner date ranges and meal headings now apply the locale's decimal style as well as its month/day names. The pantry invalid-date validation uses the existing translated error resource. These are presentation changes; stored dates, quantities, recipe names and user text are unchanged. Shared host/Fire checks include all 12 resource contexts and explicit Arabic integer/date expectations. Native-speaker approval remains pending.

The literal scanner now matches complete UI call names and error assignments. It no longer misclassifies the HTTP `getHeaderField("Location")` call as a UI field, and it detects dialog errors assigned before rendering. Scanner fixtures retain escaped quotes and interpolations for review; a lower heuristic count is not full UI approval.

Current Arabic host frames for the home, planner and cooking screens are retained separately in `artifacts/runtime-localization`, with source and pixel hashes. The existing store-upload compositions and their original source frames remain historical drafts, preserving their saved Amazon upload bindings; they were not silently replaced by new test renders. The updated Fire QA build passed its Arabic large-font calendar and dialog checks. These observations do not confer native-language or final store-image approval.

Runtime localization now includes 46 additional authored messages and labels in `authored/runtime-ui.tsv`. Data-layer failures have stable codes resolved at the presentation boundary; arbitrary provider diagnostics never become untranslated UI. Recipe/pantry actions, shopping categories, default difficulty labels, unknown quantities, local number formatting, exported section headings and enabled purchase guidance use resources. Exports preserve user text and canonical unit codes. Host and Fire native checks exercise all 12 locale resource contexts, exported ingredient parsing and privacy-safe error fallback; these checks do not constitute native-speaker approval.

Ingredient-quantity voice questions now have complete-command patterns in all ten supported language families (including both English and Portuguese markets). Ingredient names remain user text, and ambiguous matches produce the existing no-match response. Broader spoken number grammar, speech-provider hardware behavior and grammatical/terminology review remain separate requirements.

Resource coverage includes all 12 requested locales. Android string coverage and placeholder/plural validation are technical gates, separate from publication approval. No locale is approved for release yet.

The initial navigation copy was authored locally. Expanded drafts combine cached Google public-endpoint translation output and explicitly authored multilingual interface copy in `authored/interface.tsv` and `authored/hi-additional.txt`. The provider throttled generation; network requests were stopped, and the remaining resources were completed locally. Only public application copy was processed. User recipes, backups, microphone audio and databases were never inputs. `finish_locale_resources.py` reproduces resource assembly without network access. `compile_authored_locales.py` preserves the source-to-translation mapping.

Run `python tools/localize.py --strict` to check resource completeness. `resource_complete` does not imply `release_approved`. The legacy `complete` field remains false until the broader review is finished. The report explicitly counts remaining inline interpolations; unit labels, backend/domain errors, complete voice dictionaries, store metadata, screenshots and website translations still need additional work.

For each market, a native reviewer must verify terminology, grammar, context, button length, privacy and subscription disclosures, plurals, accessibility announcements, OCR guidance and actual rendered layouts. Portuguese resources need separate Brazilian and European review. Arabic needs RTL, numeral/bidirectional text and large-font checks. The recipe-count plural resources include the required Arabic and Polish categories; grammatical review is still required. Do not translate user-entered recipe or collection names automatically.

Keep DishNest and Amazon product names unchanged. Metric and imperial abbreviations describe actual quantities and must not silently change their units. Pasted recipes accept complete section-heading lines in all 12 app locales, independently of the device language. English `Ingredients`, `Method` and `Instructions` remain accepted for compatibility with existing guidance. Local headings include `Zutaten` / `Zubereitung`, `Ingredientes` / `Preparación`, `Ingrédients` / `Préparation`, `Ingredienti` / `Procedimento`, Portuguese `Ingredientes` / `Modo de preparo` or `Modo de preparação`, `Ingrediënten` / `Bereiding`, `Składniki` / `Przygotowanie`, `المكونات` / `طريقة التحضير` and `सामग्री` / `विधि`. Heading matching normalizes Unicode and casing without translating user content. Colon variants, common ingredient bullets and Unicode decimal step numbers are supported. This does not extend the English OCR model or establish native approval; localized ingredient-unit parsing remains separate work.

Visual localization now includes eight tablet screenshot compositions and one promotional image for each of the 12 app locales. Actual production Compose screens are rendered with isolated translated sample records, including recipe titles, ingredients, cooking instructions, collection/difficulty labels and pantry entries. Captions, preview disclosures and promotional copy are translated too; the DishNest brand icon is shared. These are host renders, not physical Fire captures. Source pixels, copy and export hashes are recorded in `marketing/screenshots/localized/manifest.json` and checked by `tools/verify_visual_localization.py`. Arabic uses RTL layout and native text shaping; Hindi uses native Devanagari shaping. This does not establish native-language or hardware approval.

Amazon's image dialog offers en-US, en-GB, de-DE, es-ES, fr-FR, it-IT and pt-BR for these target languages. It does not offer nl-NL, pl-PL, pt-PT, Arabic or Hindi artwork slots, even though the first three have description slots. Those visual sets remain available locally. Actual saved upload receipts are in `marketing/amazon-artwork-uploads.json`; do not infer upload coverage from the description locale list.

The readiness continuation adds locally authored `authored/readiness.json`, merged by `tools/compile_readiness_resources.py`. It covers dynamic summaries, meal slots, step progress, planner swaps, photo-backup guidance, filters, timer notifications and speech-service states. Exact cooking commands cover all target language families; non-English timer commands currently require digits, and ingredient quantity questions now have anchored patterns in every supported language family. The heuristic inline report includes non-copy (dates, numbers, user text and the HTTP Location header); a human full-surface audit remains necessary. No native language approval is inferred from these technical checks.

The existing store artwork and its source pixels are retained as versioned composition drafts. Host test reruns can produce candidate frames with transient cursor or layout timing differences; they do not automatically replace the recorded artwork or Amazon upload receipts. The retained compositions predate the latest runtime label and quantity changes. They remain historical drafts and require refreshed final hardware captures and native review.

Quantity parsing now accepts Unicode decimal digits (including Arabic-Indic, Devanagari and full-width digits), Arabic/full-width decimal points and unambiguous decimal commas. A comma followed by exactly three digits and grouping separators remain ambiguous without a source locale; forms reject them instead of silently changing the amount. Unsupported or invalid ingredient quantities retain the complete line for review, including invalid fractions. Common translated metric unit names map to their actual metric units, without guessing cup volumes or translating ingredient names. Unit labels are now localized at display boundaries. Expanded parsing aliases, vocabulary and native review remain pending.

The date/copy build passed 96 host tests, six Fire native checks and the 15-test Fire UI/native suite. The new Arabic flows verify the saved duplicate label and preservation of the original recipe, and localized meal-swap dates with canonical storage. One separately retained Arabic pantry host frame was visually inspected; it is synthetic host evidence, not final store or native-language approval. See `artifacts/runtime-localization/date-copy-evidence.json`. Existing Amazon artwork and source frames retain their historical upload bindings.

The in-app selector uses the existing 12 resource sets and supports device-language reset. Its three new strings require native review like the other drafts. The initial priority languages Japanese, Korean, Simplified Chinese, Traditional Chinese, Turkish, Indonesian and Swedish are not implemented; the validator reports them separately rather than treating 12-locale resource completeness as full worldwide coverage.
